## 先给运行器：可冻结的工具原文

下面是一条完整的 **模型原始文本**；不是协议 JSON 或 SSE 帧。先用关闭 thinking、启用工具解析的请求，最好声明同名函数及 `location: string` 参数，再依次输入 Ready、Text、后端 Finish(Stop)。

```text
<｜DSML｜tool_calls><｜DSML｜invoke name="get_current_weather"><｜DSML｜parameter name="location" string="true">Tokyo</｜DSML｜parameter></｜DSML｜invoke></｜DSML｜tool_calls>
```

源码预期工具名为 `get_current_weather`，参数 JSON 语义为 `{"location":"Tokyo"}`。Chat/Responses 的 arguments 是字符串，格式可能含空格；Messages 累积后是 input 对象。名称和参数都完整时，后端 Stop 对应 Chat `tool_calls`、Messages `tool_use`、Responses `completed`。

- 空参数调用可以用 `<｜DSML｜tool_calls><｜DSML｜invoke name="f"></｜DSML｜invoke></｜DSML｜tool_calls>`，参数预期 `{}`。
- `string="true"` 会把值转义为 JSON 字符串；`string="false"` 原样写值，如 `2`、`true`、`{"x":1}`。解析器不因此校验 JSON、工具参数 schema 或实际函数是否存在。
- Tokens 输入时，`｜DSML｜` 是真实特殊 token；`<`、`</`、`invoke name=...`、`parameter name=...` 是普通部分。先编码完整原文再切同一 ID 序列，不能把特殊 token 拼写拆开重编码后仍当等价输入。
- 开始工具分支实际由 `<` + DSML 特殊部分触发，并不是严格 XML 校验；规范样例应使用上面的完整闭合结构。源码还接受带空格的 ` calls>` 等形式，不建议把宽松接受误写为唯一标准语法。

依据：O:390–567、P:695–750、P:1085–1122。

## 入口、分组和收尾职责

源码链：`InferenceChunk → StreamDecoder（仅 Tokens）→ OutputParser.feed → PendingOutput → 各协议 ChunkGenerator → 协议事件 → Response.accumulate`。

| 层 / 入口 | 实际职责 | 不应混同的边界 |
| --- | --- | --- |
| `InferenceChunk.ready` | 后端提供 prompt token 数、缓存命中数、可选 fingerprint | 不从请求文字自动统计 prompt usage |
| `InferenceChunk.text(str, token_count=0)` | 接受有效 Unicode 字符串；整段为一个 `ChunkKind::Text`，标记按拼写识别 | 没有特殊 token 身份；附 tokenizer 也不会自动补算 completion 总数 |
| `InferenceChunk.tokens(ids, logprobs)` | tokenizer 把普通 ID 段解码为普通 piece；每个特殊 ID 单独成为 special piece | 一次 push 可能变成多个 parser feed；不是 SSE 字节流 |
| 内部 `OutputParser.feed(content, kind)` | 按字节推进有状态匹配，跨 feed 保留部分标记；返回 action 和输入字节长度 | `feed` 不是 Python 暴露的公共方法 |
| 内部 `OutputParser.finish(self)` | 把未匹配完的标记按当前阶段的 unmatched action 处理 | 不补齐工具标签、引号或 JSON，也不自行声明后端 Stop |
| Python `processor.push(chunk)` | 投递一个后端更新，排出 Rust 再次需要输入前可得到的事件 | 不保证每 push 恰好返回一个事件，也不保证立刻吐出所有普通前缀 |
| Python `processor.finish()` | 关闭输入通道并排空；无后端 Finish 时内部原因是 EndOfStream | 这是正常关闭输入，不是网络异常或客户端取消信号 |
| Python `processor.close()` | 释放 processor 状态，不产生成功收尾事件 | Response 中已积累的部分内容独立保留；不自动回滚，也不追加终态 |
| `Response.accumulate(event)` / `to_json()` | 按顺序消费协议事件并序列化当前状态，包括部分状态 | 不是另一套完整原始输出解析器 |

依据：I:1–95、D:165–252、P:95–232、O:104–141 / 603–665、B:334–337 / 446–543。

Tokens 的三个实际分组规则需独立测试：

1. 普通 token 尾部解码为空或 U+FFFD 时暂存，等后续 token 补齐；成功解码后此前暂存 ID 一起计数。EOF 时仍未解码的 ID 不输出，也不计 completion。
2. 真实特殊 token 到来前会强制 flush 普通前缀，即使前缀仍是 U+FFFD；随后特殊 token 单独解码。这与单纯 EOF 丢弃不同。
3. Text 路径没有 token 身份；Tokens 路径能区分真实 `</think>` / `｜DSML｜` 和普通 ID 拼出的同名文字。把 Text 和 Tokens 只按解码后字符串相同来比较，会丢掉这个前提。

依据：D:9–13 / 165–252，P:1033–1147；现有 T:487–578 还覆盖逐 ID 字符和无效 ID。`999999999` 被忽略是既有上游测试中的 tokenizer 行为，不能把它推广为所有 tokenizer 错误都忽略。

## thinking、stop 和工具块的状态边界

- `starts_in_tool_calls=True` 优先于 thinking 初始阶段；适用于 prompt 已经打开工具块的续写，此时原文应该从块内继续。普通最小样例使用默认 False。
- `ReasoningStart` 丢开头换行；`ReasoningContinuation` 保留；`ContentContinuation` 从答案开始且保留换行。默认非 thinking 的 Content 也去开头换行。Reasoning→Content 时还会去掉 `</think>` 周围的相关换行；不是所有 whitespace 都可随意归一化。
- 工具块可以直接结束 reasoning，不要求先有 `</think>`；Content 里的多余 `</think>` 会被跳过。工具块关闭后进入 parser 的 Finished 阶段，后续文本被忽略；**processor 仍可等候后端 Finish/EOF，后续输入也仍可能计入 usage**。
- stop 仅匹配答案 Content 或已经识别出的 JSON 内部，不匹配 Reasoning、工具标记或 JSON 外围文字；空 stop 被移除。其前缀可跨块缓冲和回退。多个分支在同一字节完成时以注册顺序优先；不会为了较长的重叠 stop 自动继续等待。
- stop 是普通文字模式；Tokens 中 special piece 不按普通模式匹配，Text 中则按拼写匹配。带特殊 token 拼写的自定义 stop 不宜预设两条路径相同。
- `parse_json_output` 只是识别裸 `{` / `[` 或 JSON fence 并把外围文本变空格，不校验 JSON。外围文本按其所跨源 chunk 产生空格，因此 `json{}` 的完整字符串可能随分块不同；不得用宽泛“任意分块逐字符一致”掩盖这个有意转换。

依据：O:35–58 / 104–128 / 390–600，P:175–197 / 643–693 / 760–824。

## 终止原因必须分三层记

处理器先记录后端原因、在后端结束时是否已有**命名完成**的工具调用；最后 flush parser，才选出内部 FinishReason。单有 ToolCallBegin 或在最后 flush 才形成的调用，不应该无条件改写 Stop。

| 内部原因 / 触发 | Chat | Messages | Responses |
| --- | --- | --- | --- |
| 后端 Stop，无已命名工具 | `stop` | `end_turn` | `completed` |
| 后端 Stop，已有命名工具 | `tool_calls` | `tool_use` | `completed` |
| 后端 Length，含工具截断也一样 | `length` | `max_tokens` | `incomplete`，reason=`max_output_tokens` |
| 后端 ContentFilter | `content_filter` | `refusal` | `incomplete`，reason=`content_filter` |
| processor 实际命中 stop | `stop` | `stop_sequence`，携带命中串 | `completed` |
| 输入 EOF，未收到后端 Finish | `stop` | `end_turn` | `completed` |

`finished=True` 只表示 Rust 流正常排空且 processor 尚未 close，不证明收到过后端 Finish。EOF 映射为 completed 是源码既有行为，实验账本应另外保留“后端 Finish 是否出现”；协议 completed 不能替代这项证据。把客户端断开直接走 `finish()`，会得到本表 EOF 的正常协议收尾；取消路径用 `close()` 才能观察没有新增终态的部分响应。

后端适配还有一条合约：后端的最后更新同时带 token IDs 时，只有 Length 应把这些 IDs 另送 Tokens；其他 finish reason 要丢弃。这里是 I:66–71 的调用方义务，库不会替适配器识别“末次 ID 是否已转发”。不能把该约定扩展为丢弃此前所有输出。

依据：P:95–139 / 209–232 / 335–344；C-schema:143–153；M-schema:82–91；R-gen:476–517。

## usage 来源和协议表达

| 字段 / 层次 | 源码来源与预期 |
| --- | --- |
| prompt / cache hit / fingerprint | 首次输出开始前的 Ready 提供；无 Ready 默认 0 / 无 fingerprint。已经开始后再 Ready 不更新生成器发出的元信息，不能靠 late Ready 修补 usage |
| Text completion 总数 | 已处理 Text 的显式 `token_count` 之和，默认 0。即使附 tokenizer，也不重新编码 Text 来补 completion |
| Tokens completion 总数 | 已成功解码并处理的 piece 中 ID 个数；包括被跳过的控制标记，不是最终可见答案字数。仍缓冲在 decoder 中的 EOF 尾 ID 不计 |
| stop 处的 completion | 在 parser 识别 stop 前先计当前 piece 的 token 数。Text 会计入整块，含 stop 之后同块尾部；后续块不再读。Tokens 按 decoder piece 处理，特殊 token 可把一个后端 chunk 切成多个 piece；不能简单断言“整次 Tokens push 的所有 ID 总会计入” |
| reasoning_tokens | 初始 thinking 阶段非 None，且 tokenizer 能计数时，重新编码**已经输出的 reasoning 内容**。不是后端逐 token 归因；可发生 Text completion=0 而 reasoning>0。D:80–84 使用 `encode_fast(text,false)`，false 表示不额外添加特殊 token，不等于排除全文词表中的特殊 token 拼写 |
| Chat 表达 | 有测量才有 `completion_tokens_details.reasoning_tokens`；非 thinking 去掉 details。prompt cache miss 用 saturating subtraction；总数是 prompt+completion。`include_usage` 影响中间 chunk 的缺省/null，源码最终 chunk仍附 usage |
| Responses 表达 | 总 input 包含 cache hit；无 reasoning 测量时 `output_tokens_details.reasoning_tokens` 填 0，账本需另标 unmeasured |
| Messages 表达 | `input_tokens=max(prompt−cache_hit,0)`，cache 单列；output 来自 completion；此 schema 没有 reasoning token 细分，不能把缺字段写成测得 0 |
| logprobs | 来自 Tokens 输入，库不计算概率；每 ID 一个条目，数量不符关闭 processor。不是无效 token、decode error、无 tokenizer 都可以统一忽略 |

切分 Text 时若想比较总 usage，必须保持各块 `token_count` 总和；不能默认每块填 1，也不能把各碎片分别重编码后相加当成原后端 token 数。stop 提前结束和 decoder 不能解码的尾部，应另作明确的非等价计量案例。

依据：I:1–24；P:57–73 / 109–124 / 175–197 / 223–227；D:74–93 / 182–252；C-gen:79–103 / 210–229；C-schema:207–245；R-schema:284–320；M-schema:101–130。

## 完整响应、事件和 SSE 的证据边界

Python 暴露的是 `Response(...).accumulate(event)`；B:239–250 使用 `inner.take()` 消费事件，`to_json()` 可以序列化部分状态。事件应先保存 JSON 和 `sse_event_name`，再 accumulate；之后重读、二次 accumulate 都会报 consumed。同一 generator 也被 StreamProcessor 构造消费。

因此“一块原始输出 vs 多块原始输出”是**同一解析器在不同输入分块下的对照**。最终响应与流事件不是两个独立的实现 oracle；Responses 终态还带最终 response 快照，累积器用它覆盖已有状态，漏掉中间 delta 可能被掩盖，必须单独检查事件序列。

Messages 的累积器会在 ContentBlockStop 时解析拼接的 `partial_json`；失败则把 tool input 回退为 `{}`。Chat/Responses 保留 arguments 字符串。截断、`string="false"` 非法值等情况下，必须比较**原始参数 delta + 最终字段 + 原因**，不能只看 Messages 最终 input 是合法对象就宣称工具参数完整。

跨运行比较时：工具调用 ID 含随机成分，比较非空、唯一性、调用次序和前后关联；生成时间也不作语义等价条件。不同协议的 ID、event 数、文本/思考 block 组织不要求相等。Messages 的 thinking signature 默认是 response ID，不能当作模型签名或推理真实性证明。

| 协议 | SSE event name | 完成 framing |
| --- | --- | --- |
| Chat | `None`，无名 data event | `sse_done_data()` 返回 `[DONE]`，由传输层另外包装发送；它不是 processor 产出的 JSON chunk |
| Responses | 与事件 type 对应；起始 `response.created` / `response.in_progress` | 完整时 `response.completed`，受限结束时 `response.incomplete`；无额外 `[DONE]` |
| Messages | `message_start`、content block、`message_delta` 等，首 block 还可有 `ping` | 最后 `message_stop`；无额外 `[DONE]` |

库给出事件对象和 framing 元信息，调用方负责 `event:` / `data:`、分隔空行及 UTF-8/字节传输。离线 framing/解码测试可以检查自己的适配层，但这不证明实际 HTTP 服务、断线传播或网络字节切分兼容性。此分工没有启动服务。

依据：A:7–44；B:190–265 / 334–337；C-schema:248–312；M-schema:209–267；R-acc:7–17；R-gen:380–397 / 476–517；M-gen:68–91 / 199–218；T:991–1025。
