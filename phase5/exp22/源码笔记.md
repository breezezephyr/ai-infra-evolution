# exp22 源码笔记：调度循环、交叠与确定性

2026-10-26；DeepInfer固定`9bd9cf243fc53ef9afbf8f04d391d989117d6ab9`。本地副本在`../vendor/exp22-source/DeepInfer`，11份固定commit原始文件及SHA256见其`manifest.json`；不是完整Git checkout。DeepInfer未安装/未执行，以下是源码可见行为；RTX4060实验运行独立vLLM/Qwen后端。

## 一、从请求到输出回收

```text
LLM.generate → _add_request（编码/复制参数）
→ LLMEngine.add_request → Sequence → scheduler.add_sequence
→ LLMEngine.step → C++ Scheduler.schedule
→ _execute_model_async_step → Worker.execute_model_step
→ ModelRunner.execute_main_model → execute_sample
→ Worker._post_process_step → engine.post_process
→ scheduler.process_outputs → build_request_outputs
→ RequestOutput.clone → 最后flush_inflight_reqs
```

入口`entrypoints/llm.py:129–190`先提交所有输入再循环step；没有未完成请求时仍flush，返回输出需要clone，因为池中的原始输出在下一次step时可回收。引擎`engine/llm_engine.py:860–1015`包含schedule、worker派发与回收；不能把Python方法名中的async当作HTTP异步服务已经存在的证明。

`csrc/engine/scheduler.hpp:275–340`的NORMAL引擎在DP组内协调本轮prefill或decode。ALL点要求各rank都有意愿，ANY点由至少一个rank触发，并在实际没有排出任务时回到decode；这是DP组内步型协调，与外部请求负载均衡职责分开。

## 二、ZOS安排的是交接顺序

`worker/worker.py:89–189`的decode路径可概括为：

| 阶段 | 当前步t | 上一步t−1 |
|---|---|---|
| 先发起forward | 当前步模型计算 | 待回收 |
| 再做post-process | 设备上的forward可仍在执行 | 等sample完成，处理结果并更新状态 |
| 再发起sample | 当前步采样 | 已处理 |
| 本步收尾 | prompt/非ZOS当步post-process；ZOS decode保存到下步 | — |

这是调用关系示意，没有用本次小卡实验测DeepInfer的设备时间。源码仍有显式同步：seqlens修正需等待D2H事件，`_post_process_step`需`sample_end_evt.synchronize()`，最后flush也可引起CPU/GPU同步。`model_runner.py:308–367`在forward/sample launch内使用`forbid_cuda_sync()`，只说明这些局部区域避免同步，不能推出整个循环无同步或调度耗时为零。

## 三、默认值必须读到构造之后

- `environ.py`底层ZOS默认False。
- `EngineArgs.engine_type`默认NORMAL；`arg_utils.py:48–55`按engine_type的属性调用`os.environ.setdefault`，随后`environ.rearm`重置缓存。
- `engine_type.py:11–17`：NORMAL/COMPLETION默认启用ZOS，PROMPT默认不启用。
- 已有环境值会被setdefault保留。因此“底层False”和“标准离线NORMAL默认启用”同时成立。部署时必须检查构造后有效配置。

本轮没有构造或运行DeepInfer引擎，不捏造其运行时有效值。实际执行的vLLM配置由插桩`engine_request.effective_config`记录：V0、eager、max_num_seqs4、max_num_batched_tokens4096、chunked_prefill=False。prefix_caching字段原值None，当前V0 scheduler的`if not self.cache_config.enable_prefix_caching`分支将其视为不启用；不把None改写为声称来自配置的False。

## 四、batch invariant与固定种子是不同条件

[官方固定版README](https://github.com/deepseek-ai/DeepInfer/blob/9bd9cf243fc53ef9afbf8f04d391d989117d6ab9/README.md)说明batch-invariant为NVIDIA路径，通过`DEEPINFER_BATCH_INVARIANT=1`启用；确定性采样还需`DEEPINFER_ENABLE_MTP_VARLEN=0`与固定`seq_seed`。这里不能写成关闭所有MTP，条件针对可变长度开关。

`tests/models/test_batch_invariant.py:52–105`先批量自由生成64条随机token输入，再逐条重放，把批量轨迹写进`golden_token_ids`，严格比较token、logprob、top-token、top-logprob。`sampler.py:650–677`的`torch.where`会用golden token覆盖采样结果，这是teacher forcing：后续概率计算沿同一条已知轨迹前进。

这个测试对数值/概率的batch invariance有价值，不能转述成两次自由随机生成天然相同。exp22的Qwen实验没有teacher forcing，以temperature0贪心自由生成实际token序列；固定seed17只是冻结设置之一。该实验不验证DeepInfer功能，也不证明随机采样、其他硬件/精度/版本的确定性。

## 五、本轮vLLM插桩范围

安装版本0.8.5；实际源文件哈希与模型文件身份见`../results/exp22/backend-identity.json`。`backend_audit.py`仅给独立服务插桩：

- HTTP `X-Request-Id`经`serving_engine._base_request_id`形成`chatcmpl-<id>`；API入口记录原始body摘要/状态。
- `AsyncLLMEngine.generate`完成时记录实际`RequestOutput`的输入和输出token IDs、finish reason、RequestMetrics。
- `Scheduler.schedule()`返回后记录该CPU调度计划的request IDs、token_chunk_size、prefill组数。非多步调度配置下，每次计划可观察同批人数；这些记录不等于CUDA kernel trace。
- `RequestMetrics`的arrival/first_scheduled/first_token/finished从同一后端时钟求差；主机调度到完成时延不叫纯GPU执行时间；没有使用缺省为None的model_forward_time/model_execute_time填造GPU数据。

本轮HTTP响应非流式，客户端完整响应耗时不能叫客户端TTFT。客户端、网关在同一台Mac用monotonic；后端时钟只在后端内部比较。SSH、网络、HTTP预处理和响应封装存在于完整响应时间里，不从两个异地主机绝对时间戳推算单向网络耗时。

## 审校补充：同机墙钟不保证连续

本轮3条RequestMetrics墙钟跨度与同机单调时钟观察区间冲突，具体ID见review-resolution。不能仅因同一主机、同一time.time调用就保证时长有效。保留原始数据，旧total/scheduled-to-finish墙钟区间不聚合；新增观察区间严格使用backend_monotonic_ns，并明确它不是精确的模型forward时长或首token边界。旧首次排队/首token墙钟汇总排除这3条并列出样本数变化。未来新运行应在每个边界直接记录单调时钟；本轮没有补跑或猜测修补。
