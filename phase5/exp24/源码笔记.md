## 单机配置与数据流

```bash
mooncake_master --rpc_address=127.0.0.1 --rpc_port=50240 --metrics_port=9024
```

### formal-v1、跨进程 v2 与 formal-v3 的记录边界

同一个 owning client 自己 `put/get` 可能命中本地复制路径；保留 v1，不能把它写成跨进程 TCP 传输验证。v2 从开始就用独立 reader B，A 持续提供存储，B 不贡献存储：

```python
# 只展示参数；分别在两个独立进程初始化，不是本文的执行记录。
MiB = 1024 * 1024
# A: setup("localhost", "P2PHANDSHAKE", 512 * MiB, 32 * MiB,
#          "tcp", "", "127.0.0.1:50240")
# B: setup("localhost", "P2PHANDSHAKE", 0, 32 * MiB,
#          "tcp", "", "127.0.0.1:50240")
```

固定源码明确支持 TCP 下 `global_segment_size=0`：跳过挂载循环，local buffer 仍照常注册（[M5:1193–1239、1342–1352][M5]）。B 的 32 MiB 是接收缓冲区，不是可分配对象的 global segment，单次读取仍受可用 buffer 容量约束。仅 A 提供存储且只由 A 写入时，无需额外指定 preferred segment。

这支持跨进程设计，**尚未证明已安装 wheel 的某次 get 确实经过 TCP**。主任务还需核对 A/B 不同的实际传输端点、对象副本归属与传输证据，并排除 B 的本地 hot cache；global=0 本身不等于关闭 hot cache。读取可重定向到 hot cache（[M4:1424–1471][M4]）；P2P 模式下本地副本判断比较实际 endpoint，不能只比较 `localhost`（[M4:5687–5696][M4]）。

### MC_STORE_MEMCPY：开关、逐次分支与证据

评审反馈有 `MC_STORE_MEMCPY not set, auto-detected: TCP-only environment, memcpy enabled` 日志。它与固定源码的初始化日志一致，只说明开关自动启用；日志字符串既不证明 wheel 对应本提交，也不证明任一 payload 已选本地复制或 TCP socket。主任务的运行口径为 **“TCP 配置的跨进程 Store API；native payload 分支未追踪；不作为纯 TCP 性能证据”**。主任务已报告 formal-v3 完成；recorder、正式数据与断言结果由主任务维护，本笔记没有独立检查或执行这些运行产物。

| 配置 | 固定源码的解析与生效时间 |
|---|---|
| 未设置 | `TransferSubmitter` 构造时令 `memcpy_enabled_ = engine_.isTcpOnly()`，不是每次 get 重读环境 |
| `0 / false / no / off` | 显式关闭 Store 的 `LOCAL_MEMCPY` 捷径；若要约束 A 的 put 和 B 的 get，应分别在两进程 setup 前设置，例如 `MC_STORE_MEMCPY=0` |
| `1 / true / yes / on` | 显式允许该捷径，仍须满足下述 endpoint 条件 |
| 非法值 | 警告后回退为 **enabled**。解析不去除首尾空白，`" 0 "` 非法；`enable/disable` 也被专门拒绝。字母值不区分大小写 |

来源：[M7:1073–1108][M7]、[M8:14–33][M8]、[M9:20–59][M9]。上述设置是固定源码说明，本任务没有修改任何运行环境或脚本。

普通 MEMORY 副本的 scalar 交接为 `Client::TransferData → TransferSubmitter::submit → submitMemoryReadOperation/selectStrategy`。逐次条件准确地是：

```text
E = handle.transport_endpoint_
LOCAL_MEMCPY ⇔ memcpy_enabled_ && E 非空
               && (E == local_hostname_ || E == local_endpoint_)
否则 → TRANSFER_ENGINE
```

`local_endpoint_` 来自 `engine.getLocalIpAndPort()`；比较是完整字符串精确相等，不能把同机或相同 IP 当成同进程。源码明确说明另一进程的虚拟地址不能直接 memcpy。CPU 本地分支最终调用 `std::memcpy`；另一分支组装 TE 请求并提交（[M7:754–765、1080–1085、1111–1137、1771–1840、1898–1914、2077–2099][M7]）。

B global=0 只排除 B 作为 global 存储贡献者，不会自动把 `memcpy_enabled_` 设为 false。若 A 是唯一 owner、B 无 hot-cache 重定向，且对象 E 与 B 的上述两个标识都不同，则**按本固定源码**，B 的 Store 本地复制条件为假，应进入 TE；这是有前提的源码推论，不是已安装 wheel 的逐次分支观测。A 向自己的副本 put 仍可能走本地复制，因此跨进程 get 也不能把整组 put/get 称为纯 TCP 数据路径。

还须区分 **Store 的 LOCAL_MEMCPY** 与 **TE 内部 transport**：classic `isTcpOnly()` 检查安装的 transport map，先忽略 `shm`，剩下恰好一个 `tcp` 即为 true；所以 `tcp+shm` 也能产生上述日志。启用 TENT 的 wrapper 则直接返回 false，不走该自动启用判断（[M10:333、1117–1123][M10] → [M11:418][M11] → [M12:977–982][M12]）。这不证明本轮 wheel 启用了 SHM；它说明仅凭 TCP-only 日志或选中 TE，仍不能排除其他 payload 路径。`MC_STORE_MEMCPY=0` 也不是整个 TE transport 选择器的 TCP-only 开关。

固定源码确有 `VLOG(1)` 的逐次策略日志（[M4:4733–4763][M4]）与 memcpy 提交日志（[M7:1758–1768][M7]）；这些位置可指导后续取证，**本文没有采集到它们**。即使取得策略记录，也应关联具体对象、操作、进程和 endpoint；若要声称经过 TCP socket，还需相应 transport/socket 证据。通用 Store 字节计数在两种策略提交后都会更新，不能单独用作网络字节证据（[M7:1156–1159、2117–2133][M7]）。Python `get` 还会复制返回的 bytes；API 耗时不等于裸 TCP 吞吐。

## API：重复、缺失、错误与租约

| API | 固定 C++ Store 源码语义 | 来源 |
|---|---|---|
| `put(key, bytes, config=...)` | 成功 `0`，失败负错误码。已存在的键在 master 返回 `OBJECT_ALREADY_EXISTS` 后，被客户端转换成成功；旧值不被覆盖。`0` 不能证明这次 payload 已写入，也不能证明与旧值相等 | [M1:3196–3210][M1]；[M4:2016–2036][M4]；[M6:5214–5219][M6] |
| `get(key)` | CPU 路径成功返回 `bytes`。未初始化、缺失、副本未就绪、查询/RPC、分配或传输失败均可能得到 `b""`；不是逐类返回负码的接口 | [M1:656–688][M1]；[M5:3842–3896、3954–3964][M5] |
| `is_exist(key)` | `1` 表示有可读副本；`0` 表示缺失或无可读副本；失败返回具体负码，不只 `-1` | [M5:2971–2987][M5]；[M6:2873–2900][M6] |
| `remove(key, force=False)` | 删除成功 `0`；缺失 `-704`；非 force 时有效读租约阻止删除，返回 `-706`。仍可能有其他错误 | [M1:2600–2609][M1]；[M5:2903–2917][M5]；[M6:7302–7324][M6] |

**存在检查有副作用，也有竞态。** Python 中负整数也是真值，因此应判 `ret == 1`，不可用 `bool(ret)` 当作存在。`is_exist` 命中和 `get` 查询都会授予/刷新读租约；固定 master 默认 10,000 ms。刚读完或刚查过存在，普通删除返回 `-706` 可以符合设计（[M6:2863–2898、4598–4601][M6]；[M3:42–55][M3]）。

`is_exist` 与前后一次 `get` 是独立 RPC；两者之间可能发生写入、删除、驱逐、故障或副本状态变化。存在检查还会改变租约。因此先查/后查存在都**不是原子 get 结果分类**：`get()==b""` 加 `is_exist()==0` 不能充分证明原次读取只是 miss；存在检查为 `1` 也不证明原次 get 已成功。正式记录应保留各次原始返回、时序、日志与可见故障信息，无法区分时明确记为“空返回，原因未分辨”。

**force 的实际边界以 master 实现为准。** `force=True` 仅跳过租约检查；所有副本仍须完成，否则 `-703`，有复制任务仍会 `-708`。Python docstring 的“跳过复制任务检查”与实际代码不一致，不能照抄；只在读写已停止后用于受控清理（[M6:7358–7375][M6]）。等待租约过期期间再次 `is_exist/get` 可能续租，不能一边轮询存在一边期待原租约自然到期。

| 码 | 含义 |
|---|---|
| `-200` | 无可用分配空间/handle |
| `-600` | 参数无效/部分未初始化路径 |
| `-703 / -704 / -705` | 副本未就绪 / 对象不存在 / 对象已存在（scalar put 会吞掉后者） |
| `-706 / -707 / -708` | 有读租约 / 传输完成前租约到期 / 有复制任务 |
| `-800 / -801` | 传输失败 / 校验不匹配 |
| `-900 / -901` | RPC 失败 / RPC 超时 |

错误码来自 [M2:303–370][M2]。scalar `get` 会合并多条错误路径，不能指望它直接返回上述所有负码。

## 重启：区分 reader、存储 owner 与 master

| 场景 | 默认 DRAM、非 HA 配置的源码结论 |
|---|---|
| 只重启 reader B，A 保持运行 | B 不拥有对象的存储副本；A 的数据可以继续供新 B 读取。是否实际恢复、何时恢复由主任务验证 |
| 唯一存储 owner A close/退出/重启 | 正常 close 清理客户端，析构尝试卸载 segment，随后释放内存；异常退出也不提供 DRAM 持久化承诺。其他副本是否仍可用需另查 |
| 只重启非 HA master | 新建 master 服务；默认 oplog 关闭。存活客户端可通过 heartbeat 执行 remount，但这不能当作旧对象索引恢复或持久化保证。即使 A 的旧字节暂留，也不等于旧 key 已可查询 |

依据：[M1:2694–2704][M1] 的 close（非零也会清掉客户端，不能把重试当成重新清理同一对象）；[M4:492–548][M4] 析构；[M5:1822–1898、1930–1942][M5] 释放；[M3:237–239、382–388、1704–1723][M3] 默认开关与新服务构造；[M4:5307–5359、5373–5386][M4] 心跳 remount。最后一行是这些分支给出的非 HA 行为推论，不是本轮重启实测；HA/oplog、SSD 恢复与额外副本均需独立配置和证据。

内部数据流为模型配置 → `_kvcache_layout` 计算各层偏移、KV/state 形状 → `allocate_gpu_cache` 分配 GPU blocks/states → `GPUCacheInterface` 按层建立视图（[D1:581–650、907–966][D1]）。`StateBlock` 区分 stored SWA 和 dropped consumer SWA/compression state；`select_state_slice_to_store` 在 128-token 粒度提取要保存的 state，`load_state_from_store_to_prefill_cache` 恢复到内部布局；`TO_CE` 的完整传递 state 与落盘片段有不同范围（[D1:32–33、221–241、763–848][D1]）。这些是引擎内部布局、分配与状态交接能力，不证明已经具备外部共享存储或可运行的 PD 服务。

README 明确本次发布提供 offline inference；完整服务仍缺 KV cache system、VE/Prefill/Decode 解耦与 prefill/decode 的 DP 负载均衡（[D0:3、38–42][D0]）。因此“内部有 cache_engine”与“完整 KV/PD 服务未随本次发布”可以同时成立；本笔记不声称 DeepInfer 已集成 Mooncake，也不把任意字节的 put/get 当作模型 KV 正确恢复。
