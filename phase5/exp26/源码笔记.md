## 观测接口

所有持久化行使用 schema `exp26.backend.v1`，包含 `pid`、`clock_domain`、`backend_monotonic_ns`、`wall_time_ns`。同一主机、进程的事件差值才直接使用此 monotonic 时钟域；跨进程/主机对齐须另有依据，不能直接相减。

`get_hook_status()` 返回本进程安装状态、9 个 hook 名称、审计错误数、映射 ID 数。`hooks_installed` 只证明安装动作；实际覆盖须另见下列 engine 事件。

| 事件/接口 | 字段与意义 |
| --- | --- |
| `http_started` | 两个 exp26 ID、`http_id`、method/path、原生 `X-Request-Id`（若有）。不记录 Authorization 等其他 header。 |
| `http_request_chunk` | `body_b64` 保留应用实际读取的原始输入字节；不预读、不回放、不额外消费 receive。 |
| `http_response_start` / `http_response_chunk` | status、原始输出 `body_b64`、`more_body`。chunk 是 ASGI body chunk，不能当成 token 或完整 SSE event；`stage=before_send` 表示发送尝试。 |
| `http_disconnect` / `http_send_raised` | 应用原本调用 receive 时观察到的断连，或 send 原始异常类型。未收到 disconnect 事件不等于连接未关闭。 |
| `http_finished` | 原始 request/response 的 base64 与 SHA256、方便阅读的 `body` / `sse`、成功返回的 send 字节 `send_returned_b64`、完整性标志、错误、实际 `engine_request_ids`。send 返回不证明客户端消费，更不证明模型停止。 |
| `engine_request` / `add_returned` / `add_raised` | 从 **AsyncLLMEngine.add_request 实参**读取实际 `engine_request_id`，与 HTTP 上下文的 request/attempt 关联。`engine_request` 是调用前映射；要结合 `add_returned` 或 `add_raised` 判断是否成功提交。提交也不等于已执行 GPU 推理。 |
| `engine_child_request` | 在 vLLM 的 `seq_id_to_seq_group` 中读取真实 child→parent 映射，不用字符串猜 ID。 |
| `engine_output` / `engine_finished` | 在原生 tracker 处理 output 前观测实际 ID、finished、输出 token IDs、原始 finish/stop reason。包含被 abort 后可能丢弃的原生输出；不表示这些输出已发到 HTTP。 |
| `abort_called` / `abort_returned` / `abort_raised` | `hook` 区分 `AsyncLLMEngine.abort`、`AsyncLLMEngine._abort`、`RequestTracker.abort_request`、`LLMEngine.abort_request`。同一次取消跨层出现多行不能重复计数。 |
| `abort_done` | **仅**底层 `LLMEngine.abort_request` 正常返回时记录；可能是 no-op。必须结合状态快照，不能把名字理解成 kernel 已停止。 |
| `state_before` / `state_after` | 围绕底层 abort、同步 step、异步 step、外层 engine_step 的状态观测。`hook` 指明位置，`engine_object_id` 标记进程内对象。`state_after.error` 非空表示原方法抛异常。 |
| `observation_error` / `engine_id_conflict` | 快照读取失败或同一实际 ID 关联不同 HTTP。相应证据不完整，不能按“缺行=空状态”处理。 |

9 个 hook：`AsyncLLMEngine.add_request`、`AsyncLLMEngine.abort`、`AsyncLLMEngine._abort`、`RequestTracker.abort_request`、`RequestTracker.process_request_output`、`LLMEngine.abort_request`、`LLMEngine.step`、`_AsyncLLMEngine.step_async`、`AsyncLLMEngine.engine_step`。

快照按每个映射 ID 分行，字段如下：

- `queues`：匹配的 waiting/running/swapped group、实际/parent ID、virtual engine、是否 unfinished。
- `cached`：匹配的 cached metadata ID 和 remaining steps；单步模式按 0 记录。cache 中保留 metadata 本身不自动算未完成。
- `tracker`：外层 `AsyncLLMEngine.engine_step` 快照包含 `active_stream`、`new_pending`、`abort_pending`；底层 LLMEngine 快照无法读取 tracker，写 `null`。
- `scheduler_unfinished`：是否有匹配的未完成 scheduler group。
- `engine_pending_or_unfinished`：scheduler unfinished 或 cached remaining steps > 0。
- `pending_or_unfinished`：有 tracker 时，合并 engine 和 tracker 三项；无 tracker 时为 **null**，不能把它当 false。
- `snapshot_complete=true`：所需 CPU 状态读取完成；读取异常写 observation_error，该次不会生成完整快照。
- `cause_engine_request_ids`：底层 abort 快照标明本次可直接读取的 abort 参数。任意 iterator 不被审计提前消费，故这个列表可能为空；仍保留原生调用和之后的队列观察。

## formal-v1 事后判定

五类 GPU case：`gpu-normal`、`gpu-pre-retry`（两 attempt）、`gpu-post-break`、`gpu-disconnect`、`gpu-drain-timeout`。前者验证自然完成；其余保留各自的注入触发点和取消路径，不能合并为一种“取消成功”。

1. 用 request/attempt/http_id 连接 HTTP 与 `engine_request`，再用实际 engine ID 查原生事件。不能把 gateway attempt ID 或 SSE 的 ID 字符串假定为 engine ID；每个 attempt 的所有映射 ID 都须纳入。存在 ID conflict 时保留 unknown。
2. 分列 gateway/client 的 close、worker join，后端 `http_finished`，各层 abort，`abort_done`，以及其后的完整 `state_after`。它们是不同端点，顺序以 raw 为准。
3. 支持“所观测 CPU 状态不再持有未完成请求”的较强证据：底层 abort 正常返回，随后 `AsyncLLMEngine.engine_step` 的成功 `state_after` 对该 attempt 的映射 ID 全部满足 `pending_or_unfinished=false`；同时保留完整 queues/cached/tracker 明细。持续观察后续 step 中是否重新出现或仍有 output；只能描述实际观察窗口。
4. 若请求在入 engine 前就被 tracker 丢弃，可能没有底层 `abort_done`。这不是缺失 GPU-stop 证据的补造机会：单列“取消在 admission 前生效”，结合 tracker/step 快照说明。
5. 若模型已自然结束，再发生 abort，`abort_done` 可以是 no-op。`engine_finished` 必须保留 stop/length 等原始原因，不能追认为 abort 截停。
6. worker join 后才出现 native abort/空快照时，明确报告取消传播 gap。即使 gateway 已顺序 join 两个 attempt，也不能据此声称 GPU/native 执行零重叠；只有相应原生时序证据才能进一步收窄结论。
7. 缺实际 ID 映射、缺后续快照、快照异常、审计写失败、独立 engine 子进程未覆盖，都记 unknown。正常完成且随后 idle 时，不会为了补证据主动 step 或轮询。

**能证明**：HTTP 层实际读取/尝试输出的原始字节；本进程原生 add/finish/abort 方法的实际调用与返回；观测时 scheduler/tracker/cache 的 CPU 状态；在已记录的后续 step 窗口中是否仍出现该请求。

**不能证明**：CUDA kernel 精确停止时刻、GPU 上绝无在途工作、请求的真实 GPU 时长/计费、跨进程时钟天然可比、send 已被客户端收到、应用 worker join 已传播到 engine，或观测窗口结束后永不再出现该请求。没有使用 CUDA synchronize、profiler 或设备 trace。

## 原行为与审计影响

模块没有包裹或替换 generate/AsyncStream generator，没有主动 abort/step、修改请求正文/header、改变调度参数、额外消费 abort iterator 或 receive。原函数收到原 args/kwargs；返回原对象，异常包括 CancelledError 原样重抛。类方法 hooks 能作用于已构造的同进程实例，但不追补加载前的活动。

记录采用同步 JSONL append 和文件锁，写失败只报警并累计 `audit_errors`，不替换原请求结果。缺 env 或版本/签名不匹配会在初始化明确失败。审计会增加 CPU/I/O 延迟，因此这是带观测的实验，不能声称耗时与未打点运行完全相同。进程崩溃/磁盘故障可导致 raw 不完整；没有 fsync 持久化保证。

ID 映射为保留后续 step 观察而持续保留到进程退出，适用于有界隔离实验。`n>1` 时需按 attempt 合并 parent/child 全部记录；本轮 gateway 未设置 n，按默认单输出运行。不要只凭某一 parent 行为空忽略 child 行。
