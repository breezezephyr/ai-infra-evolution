## 三句话

1. **门开在哪，排队就在哪，吞吐不变。** 四种门输出吞吐 351–385 tok/s，车一直是满的。pass 让 23 人在 vLLM 里等（TTFT 14.6 s），queue 让他们在网关等（9.3 s 后 503），reject 直接不让进。座位定了上限，门只决定谁在哪儿等、等多久被告知。
2. **按 token 预算准入，抢占归零，ITL p99 从 52 降到 22。** 预算 12,000 按 in + max_tokens 预留，等价于最多 9 人上车；vLLM 自己准入放 12 人、KV 顶到 100%、抢占 60 次。少坐 3 个人换来的是车上每个人的每字间隔稳定（exp1 那一跳没了），代价是 KV 只用到 84–91%。**预留满 max_tokens 是保守的账**，实际输出短于 max_tokens 时座位空着。
3. **拒绝要配退避，否则就是空转。** reject 组 6 秒烧完 256 条，只完成 9 条：客户端拿到 429 立刻发下一条，又被拒。完成数看起来惨，但车上 9 人的 TTFT 0.9 s、ITL p99 22 ms 是四组里最好的。线上的 429 必须配 Retry-After + 客户端退避，否则限流器只是把排队搬到了网络上。

## 两种超时是两回事

- **首字期限**杀的是站台上的人：172 条全在 waiting 里被 abort，一个 prompt token 没搬，服务端零浪费。但 ITL p99 跳到 136 ms（四组最差）：期限到 → abort → 座位空出 → 新人涌入搬行李 → 老乘客每圈被拖，加 20 次抢占。**杀站台上的人不浪费算力，但把车上的人颠了一下。**
- 字间停滞超时（本组没触发）杀的是车上的人，行李已经搬了，那才是浪费。P3·1 正文里两种超时分开讲。

## 对 P1 / P2 的指向

- P1 决定 2（准入）：vLLM 的准入看「现在放得下」，网关的准入看「到 max_tokens 也放得下」——两种账，后者不抢占但空座位
- P2 exp1：pass 组 TTFT 14.6 s / ITL p99 52 / 抢占 60 与 09-21 的 14.8 s / 53 / 92 同形状，实验可复现
- P2 两面对上：网关估行李走 `/tokenize`，空载 2–8 ms，reject 组高压下 p50 **43 ms**——分词也在 API server 进程里排队，与两面对上里「前端到调度器一段只在重载下可见」同源

## 没查清

- 首字期限组的 ITL p99 136 ms 是 abort 处理开销还是抢占重搬，要看窗口内 ITL 直方图与抢占时间点是否重合
- queue 组 client 完成 142、网关 ok 143、服务端 146：多的 3 条是客户端 10 s 前放弃而服务端跑完的，同 P2 e2e 差的那类
