# exp7 · 寄存箱在哪辆车上（2026-09-23 19:41–19:53）

口径：两辆 Qwen3-0.6B BF16（`bench-pair@8004` / `@8005`），同一张 RTX 4060 Laptop 8 GB，vLLM 0.8.5 V1，每辆 `GPU_UTIL=0.45`、`MAX_NUM_SEQS=32`、`MAX_BATCHED_TOKENS=2048`，KV 各 **9,952 token**。网关 `gw.py` 独立进程 :8011，`GW_MODE=pass`（不限流，只选车）。客户端 `mix.py` 闭环并发 8，每组 150 s：
- 8 组常客，每组 1,536 token 公共前缀（96 block）+ 64 随机 token，输出 64；每条约 100 block，**命中上限 96%**
- 8 × 1,536 = 12.3K > 一辆车 9.95K；前缀哈希时每辆车只装约 4 组（6.1K）
- 常客均匀或 Zipf 1.1（头部一组约占 39%）；每组换 seed 生成新前缀，上一组的寄存箱不命中
- 命中率 = 两辆车 `gpu_prefix_cache_hits / queries` 的窗口差（按 block）

| 选车 | 常客 | 命中 A / B | 完成 A / B | TTFT p50 / p90 / p99 | ITL p99 | 输出 tok/s |
|---|---|---|---|---|---|---|
| 轮询 | 均匀 | 68% / 64% | 339 / 339 | 57 / **222** / 421 ms | **190** | 264 |
| 前缀哈希 | 均匀 | **95% / 95%** | 334 / 437 | 55 / 67 / 543 ms | 39 | 302 |
| 前缀哈希 | Zipf | 95% / 94% | 301 / **484** | 57 / 68 / 441 ms | 40 | **308** |
| 有界哈希 c=1.25 | Zipf | 79% / 87% | 338 / 396 | 58 / **230** / 316 ms | 36 | 288 |

两辆车全程抢占 0。有界哈希组 734 条里改道 105 条（14%）。逐条 `exp7-*.req.jsonl`，网关 `exp7-*.gw.jsonl`，汇总 JSON 的 `servers` 字段是两辆车的计数差。

## 四句话

1. **轮询把两辆车的寄存箱变成了同一份的两个副本。** 每辆车都要装全部 8 组 = 12.3K，只装得下约 6 组，按随机访问估命中 ≈ 6/8 × 96% = 72%，实测 64–68%。前缀哈希后每辆车只装自己那 4 组，命中 95%，贴着上限。**路由决定的不是命中率，是寄存箱的有效容量**：轮询时两辆车合起来等于一辆车的容量，哈希时是两辆车的和。
2. **没命中的代价落在 p90 和别人的 ITL 上，不在 p50。** 四组 TTFT p50 都是 55–58 ms——中位数那条总是命中的。轮询组 p90 222 ms（哈希 67），ITL p99 190 ms（哈希 39）：没命中的那条要整搬 1.5K 行李，预算 2048 一圈搬完，同车的人这一圈都等着。吞吐 264 vs 302（−13%），全是重搬的行李。
3. **哈希天然不均，8 个 key 分两辆车就能偏到 43 : 57。** 常客均匀时 334 : 437；Zipf 下最热的一组和另外三组落在同一辆车上，301 : 484（38 : 62）。**但这里偏了没有代价**：吞吐 308 反而最高、TTFT 不变。两辆车共用一张卡，热的那辆批更大，decode 每圈时间几乎不变；负载轻（并发 8），谁也没排队。
4. **有界哈希在这里只付了代价，没拿到收益。** 为了均衡改道 14%，改道的请求去了没有它寄存箱的车：命中 95% → 79–87%，p90 68 → 230 ms，吞吐 308 → 288。均衡的收益要在「两辆车各自独立、热车真的排队」时才出现；这张卡上只看得见命中的那一半。

## 对 P2 / P3·1 / P3·2 的指向

- P2 exp3：寄存箱让 TTFT ÷14、KV 87% → 29%——**只在一辆车上**。这里补上多车：命中率由路由决定，轮询下 1.5K 前缀的常客在两辆车上各搬一遍
- P3·1：门只决定谁在哪儿等；P3·3：**选车决定行李搬几遍**
- P3·2 的 0.8 s（交互路上车赶上别人整块搬行李）和这里轮询组的 ITL p99 190 ms 是同一件事：没命中 = 一整块 prefill 进了别人的那一圈

## 这张卡做不了的

- 两辆车共用一张 GPU：负载倾斜的代价（热车排队、冷车空转）在这里被抹平了。有界哈希的收益要两张卡才测得出，本组结论只到「命中的代价」
- 并发 8 的轻载：没有排队，T_first = max(Q, R) + C 里的 Q 近似 0；重载下哈希到热车的排队 Q 才会和重搬 R 竞争
- 跨车搬寄存箱（书 9.5 的带宽交点）：同卡两进程之间 vLLM 0.8.5 没有 KV 迁移，只能纸面算

## 顺带查清的

- 0.6B 两实例起不来：`GPU_UTIL=0.42` + 默认 `MAX_NUM_SEQS=256` / 预算 8192 时 profile 峰值 + 权重 1.12 GiB + 系统基线 0.87 GiB 已经吃满，KV 为 0。降到 32 / 2048 后 0.45 各 9,952 token
- vLLM 0.8.5 的 `determine_available_memory` 用 `mem_get_info` 算非 torch 占用，理论上会把卡上其他进程也算进去；WSL 下实测第二辆车**没有**把第一辆算进去（两辆同为 0.45 都拿到 9,952），util 不用累加
