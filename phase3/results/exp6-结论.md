# exp6 · 谁先出首字（2026-09-23 18:06–18:19）

口径：同 exp5——Qwen3-1.7B BF16，RTX 4060 Laptop 8 GB，vLLM 0.8.5 V1（`MAX_BATCHED_TOKENS=8192`，无 priority 调度），KV 13,184 token。自写闭环客户端 `bench/mix.py`，每组 150 s：
- **交互路** 1 路：256 in / 64 out，`x-priority: 1`，每条结束后想 0.5 s
- **批处理路** 7 路：2048 in / 256 out，`x-priority: 100`，不停
- 随机 token 解码成文本，每条不同（不命中寄存箱）；重新分词后批处理每条实际 ≈ 2,400 token（+5%，同 P2），交互 ≈ 330
- 网关预算 12,000，排队上限 60 s（本组无 503）

## 四句话

1. **调度器不知道谁是谁，门口排队的顺序就是出首字的顺序。** 透传和网关 FCFS 下交互路 TTFT 都是 4 s：它排在 2–3 路批处理后面。换个地方排（vLLM waiting → 网关），数不变。
2. **网关插队，交互路首字 ÷60，批处理只让出 3% 吞吐。** p50 4.29 s → 0.07 s，150 s 里交互路完成 25 → 69 条。批处理 tok/s 156 → 152、TTFT 6.3 → 6.8 s。插队便宜，因为交互路的行李只有批处理的 1/7。
3. **优先级只管顺序，不留座位。** 优先级组 p99 还有 6.57 s：5 路批处理 × 2,400 = 12,000，正好把预算吃满，交互路排到队首也放不下，只能等一路批处理下车（网关日志：那一条 queue_ms 6,263）。给高优留 1,000 token（批处理只能用 11,000，放 4 路）后 p99 → 0.86 s，批处理吞吐 152 → 153，**没掉**——车本来就是满的，少坐一路批处理，其他路每圈更快。
4. **剩下那 0.8 s 在车上，网关管不到。** 优先级两组 p90 ≈ 0.8 s，网关日志里这些条 queue_ms = 0、从放行到首字 786–840 ms：应是交互路上车那一圈正赶上一路批处理整块搬 2.4K 行李（未与服务端时间线逐条对上）（预算 8192 允许一圈搬完）。这是 P2 exp2 的「每圈预算 = 老乘客最多等多久」，要靠调度器侧（小预算、vLLM priority）解决，不是门。

## 代价：网关比 vLLM 自己少坐一个人

透传组批处理 179 tok/s，网关三组 152–156（−13%）：vLLM 按「现在放得下」放 6 路，网关按 in + max_tokens 预留放 5 路。exp5 的「预留满 max_tokens 是保守的账」在这里是 13% 的批处理吞吐。换来的是：透传组**每一条**交互请求都被卡过（最长字间中位 512 ms），批处理 99%；网关组交互 1–8%。透传下 vLLM waiting 常驻 3 路，一有人下车就一口气放进两路批处理一起搬（一圈 4.8K），网关每次只放一路（推断，未验证）。

## 对 P1 / P2 / P3·1 的指向

- P1 决定 2（谁上来）：vLLM V1 的 waiting 队列只有 FCFS。0.8.5 里 `--scheduling-policy priority` 回落 V0；优先级只能放在门口
- P2 exp2：预算 8192 下 TTFT 好、老乘客被整块搬行李卡住——这里交互路 p90 的 0.8 s 就是这一圈
- P3·1：门只决定谁在哪儿等；本组补一句——**门还能决定谁先上，但决定不了上车后那一圈跟谁同车**

## 没查清

- 网关组交互路被卡的比例（1–8%）比按「批处理每 ~2.4 s 下车一路、交互在车上 1.3 s」估的 ~50% 低得多。猜是闭环相位锁：交互路总在一路批处理刚上完车之后上车、下一路之前下车。要看逐条时间线确认
- 透传组批处理 TTFT p50 1.1 s、p90 6.5 s 两峰，应是「空座直接上」与「在 waiting 里等」两种人，未拆
