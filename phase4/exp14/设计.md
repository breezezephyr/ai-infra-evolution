# exp14 · 一句语音的接力时间线

> 设计依据，2026-10-22。已按本设计完成exp14，实际结果见 `../../results/exp14-结论.md`，实现差异见 `progress.md`。下文保留设计时的配置与验收要求。

## 1. 要回答的问题

同一套 GPU ASR → LLM → TTS，用户说完后，时间主要花在等端点、识别、等首段文字，还是生成/传送/播放音频？缩短尾静音或提前分句合成，分别牺牲什么？

本实验以单会话/单在途回合起步，比较级联内的三个配置。Omni 只作架构说明，当前不制造一个没有跑过的性能对照。

## 2. 数据流与候选

```mermaid
flowchart LR
    C[客户端按实时节奏发送 PCM] --> V[VAD 与端点策略 · CPU]
    V --> A[Whisper small · CUDA]
    A --> L[Qwen3-0.6B · CUDA]
    L --> S[整段或分句文本缓冲]
    S --> T[Kokoro 中文 TTS · CUDA]
    T --> O[PCM 帧与事件]
    O --> P[客户端播放队列与渲染记录]
```

| 组件 | 起步配置 | 首次验收 |
|---|---|---|
| 输入/VAD | 单声道 PCM16 16 kHz；20 ms 传输帧；Silero CPU | 输入帧重组为模型要求的窗口，不能把每个传输包直接当 VAD 窗口 |
| ASR | `Systran/faster-whisper-small`；`device=cuda`，`int8_float16`；中文、beam=1 | 完整迭代 `segments` 后计完成；保存真实转写/配置，不只计返回生成器的耗时 |
| LLM | `/opt/models/Qwen3-0.6B`；BF16；关闭思考；贪心；最多96个新 token | 文本增量和实际结束原因，固定同一 system prompt |
| TTS | `hexgrad/Kokoro-82M-v1.1-zh`；CUDA；`zf_001`；输出24 kHz | 保存真实 PCM、音色/速率/文本、样本数、设备与实测 dtype |
| 传输 | 首轮 WS：JSON 控制/事件＋二进制 PCM | 帧边界/采样格式/序号完整；浏览器可重建连续音频 |

VAD 可作 CPU 策略模块；ASR、LLM、TTS 的模型推理均必须证明在 GPU 上执行。候选未安装未测通，dtype 和兼容版本以 smoke test 后锁定。

Whisper 起步在端点后转写完整回合，不叫原生流式 ASR。Kokoro 按文本片段生成波形，不把切成20 ms网络帧称为模型每20 ms增量合成。输入尾部静音是实验输入，ASR 内部自动 VAD 先关闭，以免重复切分混淆。

## 3. 资源与环境

- 为语音实验新建独立 venv，复用已有模型文件；不升级 `/root/vllm-env`。依赖安装、权重下载和服务配置变更尚未执行。
- 成功 smoke test 后冻结 Python/包版本、模型 revision、权重哈希、驱动/CUDA/cuDNN 和运行参数。PyTorch 可见 cuDNN 不代表 CTranslate2 能动态加载同一套库。
- 首先分别加载/推理，再验证三模型同卡常驻。整卡已用显存用 NVML/nvidia-smi 采样（实际实现含基线，不称精确单进程峰值）；Torch allocator 统计不能覆盖 CTranslate2 的全部分配。采样值称观测峰值，不声称捕捉所有瞬时分配。
- 单回合上下文先限制1024输入 token；音频最长15秒；输出96 token。超过上限单列失败，不悄悄截断后计成功。
- 三模型共驻/运行以最多约6.5 GiB为试验保护预算，预留余量；这是配置目标，不是测量值。若 OOM 或预算不满足，停止该配置并记录，不静默 CPU/offload。
- 远端仅回环端口，使用已建立的 SSH 转发让本机浏览器访问 localhost。该路径含 TCP 隧道，网络时延写清，后续不拿它直接证明 UDP/WebRTC 的相对性能。

## 4. 三个对照

| 模式 | 尾静音确认 | LLM → TTS | 要隔离的变量 |
|---|---:|---|---|
| A | 500 ms | 等完整回答再合成 | 基线 |
| B | 200 ms | 等完整回答再合成 | 与A只改端点等待策略 |
| C | 200 ms | 遇到句末或最多32个汉字/字符，首个完整片段送 TTS，尾段补齐 | 与B比较文本分段；同时检查首包与连续播放质量 |

500/200 ms、32字符和96 token均为实验选值，不是推荐线上默认。明确缓冲的字符/token单位。C的最短合成片段设8字符，遇到自然句末可更短，规则固定后不逐题调参。

原生模型不支持片段内部取消时，取消粒度就是一次合成调用。即使本组不压测 barge-in，断连也要等待真实 worker 收拢；不能让后台计算混进下一轮。

## 5. 输入与样本安排

1. 自写12条中文问题：6条连续短句、3条含句中停顿、3条倾向长回答的问题。保存原文和音频 manifest；本机 `say -v ?` 已列出 `Tingting / zh_CN`，拟选该独立系统音色，但尚未试合成。通过音频生成/重采样检查后固定来源、版本、音色、时长与 SHA-256，避免用待测 TTS 同时生成所有输入。不可用时记录阻塞，不伪造音频。
2. 连续短句覆盖不同长度；句中停顿用300/600 ms的受控插入样例，保存完整拼接参考与所有语音区间。离线用样本偏移检查端点是否早于参考回合的最后语音区间；该标注不提供给在线 VAD。提前触发时标记 `endpoint_early`，另记实际截到哪一段，不能作为成功的低延迟样本。客户端仍保留完整输入发送/接收证据，避免无声丢弃后续语音；后续输入怎样处理也记入终态。没有单一可信语音结束标注的样本，其相应端到端字段为 null。
3. 客户端按音频采样时间实时送20 ms帧，尾部至少保留足够500 ms端点观察的静音。不得把整段瞬时上传的耗时写成实时回合延迟。
4. 每条每模式3次，共108条；同一条内轮换模式顺序。热身另存不混入。实际成功、端点错误、超时、长度限制分别给分母；12条仍是12条独立文本，不用重跑扩充质量样本数。
5. 三组件独立基准另做：固定音频测ASR、固定提示词测LLM、固定文字测TTS。单跑与共驻路径分开，不用独立时延之和预测真实回合。

合成输入用于控制变量，不作为口音/噪声鲁棒性或通用 ASR 准确率评测。CER按预先固定的去标点/空白规范化计算，同时保留原文；没有人工真值的自由回答只做事实性较弱的可播放检查，不报告总体对话质量分数。

## 6. 事件与计时

| 时钟域 | 最少事件 | 可得的指标 |
|---|---|---|
| 服务器单调时钟 | 最后语音样本收到、端点确认、ASR开始/结束、LLM开始/首文本/结束、首片段提交TTS、TTS开始/首PCM/结束、音频写出 | 接收侧端点等待、组件/队列等待、首PCM和首发送时间 |
| 客户端单调时钟/音频sample轴 | 输入语音结束、帧发送、首PCM收到、首非静音样本渲染、播放欠载、输出sample位置 | 同端回合至接收/渲染的耗时、缓冲、输出连续性 |
| 客户端设备输出估计 | Web Audio输出时间戳，记录API支持情况 | 设备输出时间估计及其来源；不冒充声学首声 |
| 声学测量（可选） | 回环录音中的输入末声/输出起音 | 只有实际捕获时才填写可闻首声；否则 null |

输入真实末声、VAD最后speech frame、端点确认是三个不同事件。20 ms传输粒度、VAD窗口和阈值带来的边界误差写入结果。

GPU独立计时用相应运行时的同步完成边界；不要在在线生成的每个token都人为 `cuda.synchronize()`，那会改变流水线。对在线路径报告墙钟事件；需要纯GPU时间时另做隔离测量。

客户端输入结束和输出渲染使用同一浏览器的采样时钟/校准映射，保存映射锚点。服务端 `perf_counter_ns` 不直接减浏览器 `performance.now()`。没有可靠映射或输出API时保留原始事件，相关派生字段为 null。

首PCM如果以静音开头，另找首非静音样本（固定阈值和窗口），不把纯静音音频包算成首声。`AudioWorklet`处理到样本不等于扬声器已经出声，`getOutputTimestamp()`只能提供设备输出估计。首包快而后续欠载的配置不能只报首包。

只在同一条样本内沿依赖边界分析关键路径；ASR提前执行、LLM与TTS重叠时画重叠区间。禁止把各阶段p50或p95相加作为总p50/p95。主报p50、每题三轮分布和原始点；小样本p95须注明n，不以108次重复推断容量或生产SLO。

## 7. 协议、异常和收拢

- 消息携带 `session_id / turn_id / generation_id / seq`、音频格式、样本数和累计偏移。文本/音频结束用明确终态，不以WS断开推断自然完成。
- 每回合最长15秒输入；发送音频队列以最多2秒样本量为界，TTS待处理文本最多2段。慢客户端触发背压并设30秒回合总超时；溢出/超时终止并记录原因，避免无限堆积。
- 控制事件不可排在一个巨大音频写入后面；分帧有界，停止/错误优先处理。跨轮次迟到帧丢弃，错误序号或不完整样本帧记协议错误。
- LLM停止事件＋真实生成线程join；ASR/TTS推理调用若不可中断，记录“等待当前调用返回”。必须分开记录 `cancel_requested`、`worker_returned`、`thread_stopped` 与播放队列清空。
- 回合失败允许沿用已加载权重，但不能让前一轮任务继续运行。常驻权重未释放是实验配置，不用显存没有降到基线判断线程仍运行，也不声称线程退出等于全部GPU资源释放。

## 8. 验收与拟建文件

按以下顺序验收，前项失败先解决原因，不以降级掩盖：

1. 三个组件输出可用；模型运行设备/精度有证据；没有CPU回退。
2. 三模型同卡常驻并完成一个真实回合，记录进程显存及清理后状态。
3. 关键功能测试覆盖半个PCM样本/残余字节、帧序号/旧轮次、VAD帧重组、句末与尾段、超时/断连、重复取消和真实线程收拢。
4. 三组108条全部给结果或明确失败原因，原始转写、生成文本、PCM与事件可追踪；时间戳满足各时钟域内的因果关系。
5. 浏览器至少完成每模式一轮真实播放和渲染埋点；有设备输出估计则注明API。仅Python收流通过时，发布口径只能到服务器/网络边界。
6. 输出时间线、首PCM/首渲染分布、错误截断数、欠载时长/次数、CER、显存观测峰值；不要求必须跑进800 ms才算实验成功。

拟建：`prepare_audio.py`、`measure_components.py`、`pipeline.py`、`protocol.py`、`client.html`、`run.py`、`analyze.py`、`plot.py`及必要功能测试。原始结果拟放 `phase4/results/exp14/`，结论 `phase4/results/exp14-结论.md`，图 `phase4/img/exp14.png`。所有原始数据和代码保存哈希。
