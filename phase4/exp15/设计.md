# exp15 · 传输与会话

2026-10-22。承接已确认的 Phase4 分篇与用户“继续 P4·2”指令，当前会话执行。实验代码与证据保留，不改原有 router/vLLM 或系统网络配置。

## 要回答的问题

1. HTTP/WS 信令成功，是否已经证明 WebRTC 媒体可达？记录 ICE 状态及实际候选对。
2. 同一份音频，在 WS/PCM 自管缓冲与 WebRTC/Opus 内建媒体链路下，建连、首个非静音渲染与播放统计分别怎样？
3. 连接断开、推理/发送完成、客户端播放完成是否是同一状态？会话排空时实际等待哪些状态？
4. 会话归属、短时重连和新连接分配怎样避免把已有状态送到另一逻辑 worker？

## 范围与对照

- 复用 exp14 已由 GPU 生成的 WAV，保存源文件、样本率、样本数与 SHA-256。固定媒体载荷，不重跑 ASR/LLM/TTS，不把回放称为新 GPU 推理或完整语音回合。
- WS：PCM16、20 ms 包、应用层序号与 sample offset，浏览器 AudioWorklet 自管缓冲。
- WebRTC：aiortc 音频 RTP track、Opus，浏览器原生接收/解码/抖动缓冲，AudioWorklet 观察渲染。控制消息与媒体分开记录；没有 LiveKit 服务端时不冒称部署了 SFU。
- 优先使用实际可达、对称的两端路径；记录信令与媒体的真实路径。SSH/TCP 隧道与 UDP 直连只作可达性检查，不能作为纯协议速度公平对照。
- 若远端 UDP/隔离网络条件不足，使用同机浏览器与本机服务完成可重复的协议基线，并明确不代表公网弱网。不得用应用层 sleep 模拟 TCP 丢包或宣称验证重传/拥塞控制。
- 输入媒体只覆盖下行，不申请麦克风权限，不声称验证上行、AEC、真人通话、插话或多 GPU 容错。

## 会话与排空

两个逻辑 worker 共享一个实验进程，只验证状态路由，不代表两个 GPU。会话固定 owner，已有会话可在 owner 排空期间继续完成；排空 worker 拒绝新会话，新会话路由到另一 worker。记录 owner、connection epoch、turn、发送样本、播放 ACK、状态历史。

短时断线保留有界的会话状态，重连产生新 epoch；旧连接的迟到 ACK/控制不能改变新连接状态。主动断线与“已播放完”分开；没有可信播放证据不能把发送完成记成已播放。

正常排空必须同时满足：不再有未结束的任务、所有发送完成、所有已交付音频有有效播放完成证据、会话已释放。另测超时强制结束，给出明确终态，不能伪装正常播放完成。

## 指标与分母

- 同一浏览器单调时钟：发起连接/媒体开始控制 → 首个非静音样本渲染；建连与稳态媒体启动分开。没有声学回环，不填可闻首声。
- WS：收到首包、包间隔、应用缓冲、欠载样本、消费样本、完整性；初始等待和正常尾部静音不算欠载。
- WebRTC：实际候选对、协议/候选类型、codec、RTP 收包/丢包/jitter、jitterBufferDelay 与 emittedCount 差分、concealedSamples 等。缺失字段为 null，不当成零。WebRTC concealment 不直接等同 WS 欠载。
- 每个场景保留完整分母与失败；重复不扩成独立网络/设备样本。有限的本地样本不写线上 p95/SLO。
- 服务器时钟只算服务器本地差值，不与浏览器 performance.now 直接相减。
