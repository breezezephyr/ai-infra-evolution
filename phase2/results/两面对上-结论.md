# 两面对上：客户端 bench JSON vs 服务端 Prometheus 直方图（2026-09-21）

脚本 `compare_sides.py`（一次 ssh 把 18 个窗口 × 7 个直方图的 sum/count 起止值查回来，服务端 mean = Δsum/Δcount）。全表见 `两面对上-表.md`。

## 对上的

| 指标 | 客户端 | 服务端 | 差 |
|---|---|---|---|
| TPOT（18 个窗口全部） | 15.4 … 33.3 ms | 同值 | ≤ 0.2 ms |
| TTFT（并发 ≤ 8） | 128 / 195 / 395 / 860 ms | 129 / 195 / 384 / 839 ms | ≤ 3% |
| TTFT（并发 16 / 32） | 3704 / 14072 ms | 4013 / 14866 ms | 服务端高 8% / 6% |
| e2e | 4054 ms（c1） | 4320 ms | 服务端高 6.6%，全部窗口都偏高 1–7% |

- TPOT 两边到 0.1 ms 一致：decode 每圈的时间只由服务端决定，网络不参与。
- TTFT 在轻载时一致；重载时服务端反而比客户端高 6–8%。服务端 TTFT = 排队 + prefill + **一段没算进直方图的时间**（c32：排队 12554 + prefill 785 = 13339，但 TTFT 直方图 14866，差 1.5 s；c1 差 0）。这一段是请求进 API server 到进调度器 waiting 队列之间（tokenize + 进程间转发），只在重载下变得可见。
- e2e 服务端一律高 1–7%。原因两条：服务端 count 比客户端多 1（bench 工具先发一条探针请求，探针和正式第一条内容相同，所以正式第一条 TTFT 只有 20 ms —— 命中了探针留下的前缀缓存）；c1 窗口有 3 条请求落在服务端 5–10 s 桶，客户端 p99 只有 4.2 s，没查清，先记着。
- prompt token 数两边不一致：客户端 32×1024 = 32768，服务端 35665（含探针）。random 数据集是 token id → 解码成文本 → 服务端重新分词，多出 5%。压测的「输入 1024」是名义值。

## 三参数拟合（P0 那套）放到压测数据上

- exp2 每个预算一条线，输入 256 → 6K 全部点：截距 **−817 ms**，斜率 1060 µs/tok，R² 0.81。截距为负说明模型错了：6K 那组 TTFT 里有 3.4 s 排队（座位不够），线性拟合把排队摊进了斜率。P0 的三参数假设「不排队」，在这里不成立。
- 只取 ≤ 2K 的点：预算 2048 → 62 ms + 180 µs/tok；预算 8192 → 0 ms + 396 µs/tok。服务端 prefill 时间 ÷ 输入 token：并发 4 时 290–300 µs/tok，并发 1 时 125 µs/tok。客户端斜率 396 vs 服务端 300：差的 100 µs/tok 是同批 4 人一起搬行李时的等待。
- 预算 2048 斜率只有 180：小预算把大行李切成几圈搬，前两人先出首字，中位数被拉低，斜率看起来更平——就是 exp2 里说的「先后不是快慢」。
- 三参数（c1 + bt8192 ≤2K，128 条请求）：e2e ≈ 705 ms + 702 µs×in + 10.3 ms×out，R² 0.989。TPOT 10.3 明显低于两边实测 15–18，因为 in 和 out 在这组里相关（out 只有 128/256 两个值），系数分摊不干净。R² 高不代表参数对：客户端拟合能给形状，参数要拿服务端直方图校。

## 给文章的一句话

客户端看得到形状，服务端看得到原因。TPOT 两边严丝合缝；TTFT 在排队出现时客户端只看到「变慢」，服务端能拆成排队 / prefill / 转发三段；e2e 差的那 6% 里藏着探针请求、前缀命中、重新分词三件小事——对账先对条数。
