# Phase 2 · 动手：把概念变成面板上的曲线

> 第 5–8 周。P0 算了账，P1 讲了调度员每圈的四个决定和那张带指标名的生命周期图。P2 只做一件事：**把那张图上的每个指标变成一条真实的曲线**，然后亲手把它们推到极限。
> 教材：ai-infra-book 8.6（请求负载下的性能与配置选择）；vLLM benchmark 工具、Metrics 文档。
> 产出：一块 Grafana 面板、三组压测曲线、一篇（或两篇）P2。

## 一、要回答的三个问题

1. P0 算的地板（6.34 ms/圈）、P1 讲的四个决定，在真机上长什么样？
2. `max_num_batched_tokens` 从 2048 拨到 8192，TTFT 和 ITL 真的互换吗？换的比例是多少？
3. 把车塞满会发生什么——先撞座位还是先撞发动机？抢占什么时候开始？

## 三、面板：先搭再压（第 5 周）

按 P1·下 那张图，六组曲线，从上到下：

| 行 | 曲线 | 对应 P1 |
|---|---|---|
| 站台 | `num_requests_waiting`、`request_queue_time_seconds` p50/p95 | 决定 2 之前 |
| 座位 | `kv_cache_usage_perc`、`prefix_cache_hits / queries` | 决定 2 的准入 |

面板搭好、空跑一次 benchmark 确认每条曲线都动了，再进压测。

## 四、三组压测（第 6–7 周）

每组固定其他变量，只扫一个。每组产出一张图 + 三句话结论。

### 压测一：坐几人——并发 1 → 4 → 16 → 64 → 128
- 输入 1K / 输出 256 固定；`max_num_seqs` 放到 256 不做限制
- 看：ITL 随并发涨多少（P0 说 batch 8→128 只慢不到一倍，验一下）；吞吐 tok/s 的拐点在哪；`kv_cache_usage_perc` 到多少开始出现 `num_preemptions`
- 对应 P0 图卡 05、06

### 压测二：行李多重——输入 256 → 1K → 4K → 16K
- 并发固定 8；输出 128
- 看：TTFT 对输入长度的斜率（P0 客户端反推是 18–29 µs/token，这次服务端直接测）；同时 ITL 有没有被拖（chunked prefill 起没起作用）
- 加一轮：`max_num_batched_tokens` = 2048 vs 8192 各跑一遍，**这是 P1·上 的核心取舍**，要拿到自己的数字

### 压测三：常客——同一 3K system prompt + 不同 50 token 问题
- 并发 8，重复 200 次；开/关 `--enable-prefix-caching` 各跑一遍
- 看：`prefix_cache_hits` 的比例；命中时 TTFT 降多少、ITL 是否不变（P0 说「省搬不省跑」，验）；命中量是否是 block 整数倍

### 加一个：制造抢占
- `gpu_memory_utilization` 从 0.9 调到 0.5，压测一重跑，看 `num_preemptions_total` 何时动、ITL 抖成什么样
- 这是 P1·上 决定 3 的实景

## 五、两面对上（第 7 周）

同一批请求，两侧各算一次：
- 服务端：面板上的 TTFT / ITL / prefill_time
- 客户端：Phase 0 的三参数拟合 `e2e ≈ 地板 + prefill×in + TPOT×out`

对一下：拟合出的 TPOT 和面板 ITL p50 差多少；拟合出的地板里，网络 + 排队各占多少（这次排队有 `request_queue_time` 可以单独看）。**Phase 0 时只有一面，现在两面都有**——这一节是 P2 文章的落点。
